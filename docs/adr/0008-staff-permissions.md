# ADR 0008：後台多使用者與功能權限

- **狀態**：已採納
- **日期**：2026-10-29
- **決策者**：Sunkuo
- **前提**：[ADR 0001 多租戶](0001-multi-tenancy.md)、[ADR 0002 平台管理後台](0002-platform-console.md)

## 背景

一家健身房的後台常有好幾個人在用（老闆、店長、櫃台、會計），但不是每個人都該看得到教練的匯款帳號、改系統設定或 LINE 金鑰。原本只要是 `admin` 角色就能用全部功能。

## 決策

### 1. 三種身分

| 身分 | 能做什麼 | 數量 |
|---|---|---|
| 主要管理者 `owner` | 全部功能＋後台帳號（新增、權限、升降級、停用、重設密碼、移交） | 每家一位 |
| 管理者 `manager` | 全部功能；**不能**管理後台帳號 | 不限 |
| 一般使用者 `staff` | 只能用被勾選的功能 | 不限 |

後台帳號仍是 `users.role = admin`，另加 `users.staff_level`、`users.permissions`（一般使用者的功能代碼）、`users.is_active`。舊資料沒有身分時視為管理者（權限不會變少）；migration 把每家最早建立的管理員設為主要管理者。平台開通健身房建立的第一個管理員是主要管理者，之後平台加的是管理者。沒有主要管理者時（例如資料被移除），最早建立的啟用中管理員打開「後台帳號」時自動成為主要管理者。

### 2. 權限＝後台側欄的選單

儀表板、預約審核、教練管理、教練鐘點、商品管理、購買紀錄、課程管理、公休設定、會員管理、會員名單、形象網站、詢問名單、分店管理、系統設定（`services/staff.PERMISSIONS`）。教練管理、教練鐘點、會員管理、系統設定標示「含敏感資料」，但仍由主要管理者自行決定是否開給一般使用者。內建三個角色範本（櫃台、店長、會計）只是幫忙勾選，實際存的是每個帳號自己的功能清單。第一版只分「能不能用」，不分「只能看／可以改」。

### 3. 後端每支管理 API 都檢查

`deps.require_perm(*codes)`（有其中一項即可）取代原本的 `require_admin`：每個 router 檔有一個 `require_access = require_perm("<功能>")`。權限每次請求從資料庫讀，修改立即生效；停用的帳號不能登入，已登入的也立刻失效。

- 多個功能共用的讀取：會員清單（`GET /users`）開給會員管理、預約審核、購買紀錄、教練管理、會員名單、詢問名單、教練鐘點、儀表板；修改只給會員管理。手動調整堂數開給購買紀錄或會員管理。LINE 額度開給系統設定或會員名單。
- 教練的電話、匯款帳號、鐘點費只給教練管理或教練鐘點；課程的每堂教練費只給課程管理或教練鐘點。
- 會員 API（`/users/{id}`）只處理會員帳號，後台帳號一律 404，避免有會員管理權限的人重設管理者密碼。
- 會員與管理員共用的列表（預約、購買紀錄、課程、商品）讀取仍以「後台帳號看全部、會員只看自己」區分，不另外依功能限制。

### 4. 後台帳號頁（只有主要管理者）

`routers/staff.py`、`pages/admin/StaffAccounts/`：帳號列表（身分、可用功能、狀態、最後登入）、新增（初始密碼只顯示一次、第一次登入要改）、編輯權限（範本＋逐項勾選）、升級為管理者／降回一般使用者、停用／啟用、重設密碼、移交主要管理者（要再輸入一次自己的密碼，移交後自己變成管理者）。主要管理者不能被停用、降級或在這裡重設密碼。

所有變更寫入 `staff_audit_logs`（租戶表、RLS）：操作者、對象、動作、內容（例如「開啟 儀表板；關閉 預約審核」），不記密碼。

### 5. 前端

側欄與路由用同一份對照表（`components/adminMenu.tsx`）：側欄只顯示有權限的功能；直接打網址進沒權限的頁面顯示 403；沒有儀表板權限的帳號登入後會帶到第一個能用的頁面。權限從 `/auth/me` 的 `staff` 取得（`lib/permissions.ts`），登入與登出時清除快取，避免沿用上一個帳號的資料。

## 之後

- 「只能看／可以改」更細的權限、自訂角色範本。
- 分店店長（ADR 0007 第二期）：帳號再加「可管理的分店」。
